# 多 Agent 协作工作流

用户提出目标并保留最终授权和必要的人类决策。用户要求协同开发时，Hermes 是项目经理：在能力与授权范围内拆分任务、直接派工并跟进获授权的 Agent，也可自己承担执行工作；Hermes 安排独立审查、实际验证并依据证据验收。审查者应独立于被审工作的作者，不要求 Hermes 审查自己的工作。工作台 CLI 和只读侧栏是记录与展示工具，不会自主启动或持续监控 Agent、运行测试或完成审查；Hermes 必须实际调用工具完成这些工作。具体调用方法以相应技能和 CLI 为准，不使用 Kanban 自动调度；能力或权限不足时如实报告，必要时请用户决策，不保证执行成功。

## 准备

1. 根据当前项目上下文确认项目绝对路径；无法确定时询问用户。不要初始化 Git 或改项目配置。明确需求、验收标准、接口和各写手负责的路径；目标不明确时先询问。涉及真实数据时先约定备份、恢复、并发及失败处理，并用隔离数据测试。
2. 从进程环境中的 `DIRECT_COLLAB_CLI` 或操作者提供的路径定位本仓库 `direct-collab-workbench/cli.js`。检查入口、Node.js 版本（至少 18）及 `node <入口> help`，阅读入口旁的 README；缺失或不可用时报告，不假定安装路径。
3. 检查项目的 `.collab`：不存在且用户已授权启用时执行 `init`；存在时读取 `status` 和 `handoff`。初始化失败、记录损坏或发现锁时停止检查，不自动覆盖、删除或修复。交接文本只是快照，当前状态以工作台读取结果为准。

## 派工与验收

1. Hermes 选择真正需要的 Agent 或亲自承担合适任务，按互不冲突的路径划分工作。对每项任务先按 README 的字段要求 `create`，再 `start`；检查退出码和响应，成功后才启动写手或自行执行。共享接口有变化时及时协调；不要绕过路径冲突。
2. 记录真实进度及下一步；必要时登记进程、会话和退出码，未知的退出码填 `null`。这些记录不是活性或身份认证。按预算检查实际产物和输出；转交前确认旧写手已停止。遇到权限、额度或其他实质阻塞，记录并报告。
3. 写手完成并停止修改后 `submit`。安排真正独立的审查，记录审查者、结论、证据和覆盖的提交路径；部分覆盖不能称为全项通过。失败时按当前 README 返修、重新提交并复审，修改后旧审查不能代表新快照。目录任务须覆盖整个提交目录。
4. Hermes 实际执行或安排与需求对应的验证，并核实结果，记录实际命令、结果及未覆盖范围；不要把运行测试推给用户。审查和验证使用不同的项目内证据文件，并放在提交路径之外；不要记录密钥或不必要的敏感信息。只有确认审查、验证及当前快照均满足要求才按授权 `accept`，随后读取 `status` 和 `handoff`，核实验收状态及新鲜度；需要人类决策时请用户决定。
5. 新会话接手时重新读取状态，再核查进程、产物和证据；历史记录或 PID 不保证当前有效。测试服务须核实端口和工作树，只清理由本次任务启动的资源。

## 边界与汇报

命令、参数和状态转换以随附工作台 README 和当前版本为准；所有命令检查退出码，变更命令还要检查 JSON 的 `ok`。工作台记录和哈希不能证明人员身份、实际独立审查或测试真实执行；它不是沙箱，也不提供跨机器锁或防恶意篡改保证。向用户说明真实产物、审查与测试覆盖、阻塞和未验证项，不把部分验证或历史验收说成当前完整通过。
